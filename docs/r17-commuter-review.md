## 1. 你的一天

### 场景 A —— 早上 7:20，在家，出门前（车在楼下）

**你想知道的**：剩多少电？**够不够开到公司（60 km）**？到了公司能充多少？

**你看到的**（`r15/01-status-light.png` + `StatusScreen.kt:659-713`）：
- 电量环 `69%`，大字 `现在能开（公里）`，下面一行 `留 20% 保底还能开 168 公里`。
- 位置卡「新湖路 · 宝安区 深圳市」，空调/车内温度两块，胎压在**页面最底**，要滑一屏半才看得到。
- 一条灰色横幅：「没读到车机的锁车状态 —— 这不代表车没锁。」

**够不够？—— 不够，而且有一个数会骗你。**

1. **没有「公司」这个目的地。** 全 App 没有任何地方能填「公司 60 公里」，
   你只能拿 `199` 减 `60` 再对着心里的数自己算。
2. **「现在能开」用的是高速档。** 我按 `ConsumptionModel.kt:124-156` 的公式复算：
   停车时参考车速走 `consumption.cruiseKph`（`ConsumptionModel.kt:217-221` = 高速行程峰值速度中位数 = **130 km/h**），
   于是命中「110–130」档 **197.36 Wh/km**（我按 App 的分桶规则在 SQL 里复算，88 个可用样本，中位数与代码一致）。
   而**你自己的通勤实测是 161.8 Wh/km**（`drives.id=499`，49.8 km / 55 分钟 / 27.5 °C）。
   差 **16.7%**。
3. **这个差值会翻转决策。** 按你实际的 60 km 通勤：
   - 20% 电量时（标定续航 ≈ 89 km）：App 说 **「现在能开 58 公里 / 留 20% 保底 51 公里」→ 到不了公司**；
   - 市区档（168.59 Wh/km）应该是 **「67 公里 / 60 公里」→ 到得了**。
   也就是说**唯一会在你通勤里翻转结论的那个电量区间，App 给的是错的那一边**。
4. **低温完全没修，也不说。** `ConsumptionModel.kt:142-146` 的温度修正**只做热的**（`max(0, 气温 − 22)`，上限 +10%），
   代码注释写得很清楚：「库里 <10°C 样本不足，做了是编数据」。
   于是冬天早上 8 °C 时，App 会用**夏天测出来的 Wh/km** 算出一个**偏乐观 15%~25%** 的数，
   而「怎么算的」里只写「· 8°C · 已留 10% 余量」，**只字不提没做低温修正**。
5. **「到公司能充多少」要跨页找。** 充电站历史（「该站历史 41 kW · 充到 80% 约 54 分钟（7 次）」）
   在**记录页 → 右上角闪电图标 → 充电记录**里（`r17/02-charge-list.png`），
   不在车况页，也不在出发前的上下文里。

## 2. 问题清单

### P0-1 ｜ **真 bug** ｜ 汇总卡上两个「充电费用」行互相矛盾 + 一句已经过时的说明

**证据**
- `app-android/.../ui/StatsScreen.kt:350-363`：`if (sum.cost > 0) … else { KV("充电费用","未记录"); Text("费用需在 TeslaMate 网页端手填单价后才有") }`
- `app-android/.../ui/StatsScreen.kt:391-406`：`if (costSummary != null && rates.configured && sum.km > 0.1) { KV("充电费用","≈ ¥…") … }`
- 两个分支**都会执行**；`sum.cost` 恒为 0（`api/queries.go:439` `COALESCE(SUM(cp.cost),0)`，而 `charging_processes.cost` 78/78 为 NULL）。
- `StatsScreen.kt:347` 的注释「「充电费用」**只出现一次**」已被 v0.25.0 打破。

**为什么烦**：你把 App 当权威数据看。一屏里两个都叫「充电费用」的行，一个「未记录」一个「≈ ¥1,837.31」，
这不是「不够用」，是**自相矛盾**。你的第一反应会变成「这个 App 的数不可信」，
然后连本来好用的「每公里成本」你也不敢信了。而且那句「需在 TeslaMate 网页端手填单价后才有」是在**把你引到一个已经不存在的解决方案**上。

**整改规格**
1. 删掉 `StatsScreen.kt:350-363` 整个 `if (sum.cost > 0) … else …` 块。
2. 费用区改成**互斥三分支**，只出现一个「充电费用」行：
   - `rates.configured && costSummary != null && sum.km > 0.1` → `KV("充电费用", "≈ ¥1,837.31")` + 下面三行 + 注记；
   - `rates.configured && costSummary != null && sum.km <= 0.1` → `KV("充电费用", "≈ ¥0")` + `Text("这段时间没有里程，算不出每公里成本")`；
   - `!rates.configured` → `KV("充电费用", "未设置电价")` + `Text("到「设置 → 电价与成本」填家充/公共桩单价后，这里会给出估算")`。
3. 旧的「费用需在 TeslaMate 网页端手填单价后才有」**整句删除**（它描述的是服务端 `cost`，已不是本功能的取数路径）。
4. 若确实要保留服务端 `cost` 通路（`tou_rates` 配了以后的路径），单列为一行 `KV("账单费用（TeslaMate 记录）", …)`，
   与客户端估算**分行、明确标注来源**，绝不共用同一个标签。

### P0-2 ｜ **误导性表述** ｜ 「现在能开」在停车态用高速档算，且低温不修正也不说

**证据**
- `app-android/.../ui/StatusScreen.kt:663-666`：停车时 `refSpeed = consumption.cruiseKph`；
  `ConsumptionModel.kt:217-221`：`cruise = medianOf(高速行程的 speed_max)` → **130 km/h**。
- 我按 `ConsumptionModel.kt:171-224` 的分桶规则在 SQL 里复算（88 个可用样本：`distance>=20`、`wh∈[50,400]`）：
  桶 0–60 = **168.59 Wh/km**（46 样本）／60–90 = 174.26（26）／90–110 = 183.00（11）／110–130 = **197.36**（5）／130+ = 0 样本（**不建桶**）。
  130 km/h 落在所有桶外 → `ConsumptionModel.kt:99-109` 走「借用最近的一档」→ 借 **110–130 档 197.36**。
- 你的通勤实测：`drives.id=499`，49.8 km / 55 分钟 / 27.5 °C → **161.8 Wh/km**；近 12 趟 30–80 km 的通勤中位约 161.8。
- `ConsumptionModel.kt:142-146`：温度修正**只做热的**（`1 + 0.006 × max(0, 气温−22)`，上限 +10%），**低温不修**。
- `positions.outside_temp` 实测 min 6.5 °C / max 42.5 °C，**<10 °C 只有 1,470 / 56,290 = 2.6% 采样**（无冬季数据）。
- `StatusScreen.kt:729-763` 的「怎么算的」文案里有「官方标称」「按平时 130 km/h 估算」「· 8°C」「已留 10% 余量」，
  **没有一句说「未做低温修正」**。

**为什么烦**：这是你**每天看的唯一一个数**。它现在有两个毛病：
(a) 停车时按高速巡航代理算，你的实际通勤是市区档 → 系统性**低估 16.7%**；
    在 **20% 电量**这个临界区间，它说「58 公里 / 到不了」，而按你自己的通勤能耗是「67 公里 / 到得了」——
    **正好在你每天要用的那个决策点上给错答案**。
(b) 冬天不给低温修正，**且不告诉你它没给**。等 12 月你真的需要它的时候，
    它给的是一个**用夏天数据算的、偏乐观 15%~25%** 的数，而且界面上没有任何线索提示你。

**整改规格**
1. `StatusScreen.kt:663-666` 的参考车速改为**三段式**：
   `行驶中用实时车速` → `最近一趟行程的均速（≤ 60 km/h 视为市区档）` → `cruiseKph`（最后兜底，且必须标「假设值」）。
   建议直接用 `store.drives.firstOrNull { it.avg_speed_kph >= 30 }?.avg_speed_kph` 作为「你日常的速度代理」，
   并在 explain 里写清「按你日常 54 km/h 估算（市区档）」。
2. `ConsumptionModel.kt:142-146` 的温度修正**加上低温分支**，但**低温无样本时必须降级为「不给数」而不是「给一个没修的数」**：
   - 当 `outsideTempC < 10` 且模型里低温样本数 < 5 时：`trueRangeKm` 返回 `null`，
     `StatusScreen.kt:681-691` 的标题改为「**官方标称（公里）· 低温未修正**」，
     副行写「低于 10 °C，本机没有足够样本估修正值 —— 冬季请按官方标称再打 8 折」。
   - 有了 ≥5 个低温样本后，启用 `× (1 − 0.005 × (10 − 气温))`（上限 −15%），并在 explain 里显示「已含低温修正 −X%」。
3. `StatusScreen.kt:729-763` 的 explain 文案**无条件追加**一句：
   「未做低温修正（本机没有冬季样本）」或「已含低温修正 −X%」—— 二选一，取决于模型状态。
4. 20% 电量这个决策点：**同屏加一行**「按你最近的通勤（49.8 公里 / 均速 54 km/h）估算，够到公司 ✓」，
   数据源用「最近一趟 ≥30 km 的行程」，没有就显示「没有 ≥30 公里的近期行程，不给结论」。

### P1-4 ｜ **误导性表述** ｜ 「家充 / 公共桩」是按交直流猜的，界面不说，而且**没有纠正入口**

**证据**
- `app-android/.../ui/ChargeCost.kt:88-97`：`if (c.is_dc) publicKwh += … else homeKwh += …` ——
  **「家充」= 交流，「公共桩」= 直流，就这一条**。
- `ChargeCost.kt:151-166`（`estimateCost`）同理：`ac_used_kwh × 家充电价` + `dc_used_kwh × 公共桩价`。
- 全 App grep 不到「跨夜 / 低功率」等家充推断逻辑 —— `CHANGELOG.md:118-120` 的「诚实性说明」写的是
  「当前靠『交流 + 低功率 + 跨夜』推断」，**代码里没有这段推断**，文档与实现不符。
- 库里 `charging_process_cost_overrides` 表**存在但 0 行**，且 `api/` 下**没有任何一处读它**
  （`grep cost_overrides api/*.go` → 无命中）——「单场纠正费用」的通道建好了却没接通。
- 实测：30 天窗口内 4 场交流，其中 **id=43（10-02，54 分钟 / 峰值 7 kW / 4.5 度）明显不是家充**，
  却被按家充电价计价；真正的家充 id=44（617 分钟 / 峰值 2 kW）又被它拉低了占比。

**为什么烦**：App 在汇总卡下面直接告诉你「**家充电占 6%**」—— 这是一句**它并不知道的事实**。
你有家充桩，你心里的预期是「大部分电在家充」；App 告诉你 6%，你会先怀疑自己的车，
再怀疑 App。而更实际的问题是：**那 6% 里混进了公司的交流桩**，
你无法修正，也无从知道。「每公里成本」这一个数字的地基是歪的。

**整改规格**
1. **先改文案，别改算法**（改算法风险太大，且数据本来不足以判定）：
   `StatsScreen.kt:409-418` 的注记由「家充 58 度 / 公共桩 961 度 · 家充电占 6%」改为
   「**交流 58 度 / 直流 961 度**（按充电类型分，不是按地点分 —— 库里没有家充标记，无法区分家充和单位交流桩）」。
   `ChargeCost.kt:53-54` 的字段名 `homeKwh/publicKwh` 同步改成 `acKwh/dcKwh`（口径写在名字里，别藏在注释里）。
2. **设置页加「家充识别」**（`SettingsScreen.kt` 的「电价与成本」页里，`ChargeRates` 旁）：
   - 新增两个字段 `homeAcMaxMinutes: Int = 0`（默认 0 = 不启用）、`homeAcMaxPowerKw: Double = 0.0`，
     含义：「插枪时长 ≤ X 分钟**且**峰值功率 ≤ Y kW 的交流场次算家充，其余交流按公共桩价」。
   - 默认值用实测反推：本车 id=44 = 617 分钟 / 峰值 2 kW、id=45 = 636 分钟 / 峰值 4 kW 是家充，
     id=43 = 54 分钟 / 峰值 7 kW 是单位桩 → 默认 **X = 600 分钟、Y = 5 kW**（可在设置页改）。
   - `estimateCost` / `estimateChargeCost` 的分流改成「先按 is_dc 分直流/交流，再用上面两条把交流劈成家充/公共交流」。
3. **接通已有的纠正通道**（可选，P2）：`charging_process_cost_overrides` 表已存在，
   在 `api/queries.go:318-406` 的 `sqlCharges` 里 `LEFT JOIN` 这张表，
   把 `overrides.cost` 作为一个**独立字段** `manual_cost` 下发；App 在充电详情页显示「手动指定费用 ¥X（覆盖估算）」。
   这样「某次充电我觉得不该有/该多少钱」有了出口。

### P1-5 ｜ **体验改进** ｜ 出发前的「够不够到公司」没有任何落点

**证据**
- `app-android/.../ui/RoutePlan.kt:261-263`：`buildRouteTemplates(…, minDistanceKm = 200.0)` ——
  **线路模板只收 ≥200 km 的行程**；`RoutePlan.kt:603-607`：`pickRouteTemplate` 默认取「最近走过的那条」。
- `r15/05-records-light.png`：记录页顶部常驻一张「**线路余量表 · 广昆高速 → 城东路 · 不用中途充电，但第 252 公里只剩 16%（低于 20% 保底）**」+ 一排 chips。

- `RecordsScreen.kt:253`：`planSpeedKph = 90.0` 写死；`RoutePlan.kt:502-519` 的「到下一站剩多少」
  **只用了 Wh/km**，**没有温度修正、没有爬升修正、没有安全余量**（跟 `ConsumptionModel.trueRangeKm` 的口径不是一套）。

**为什么烦**：每天早上你要的那句「够不够到公司」，App 用一个 **≥200 km 的长途余量表**回答你，

两个数放在一起会打架。

**整改规格**
1. **把「线路」的门槛从 200 km 降到 40 km**，并让 `buildRouteTemplates` 的参数按「最近一趟行程的距离」自适应
   （`minDistanceKm = min(200, 最近一趟 ≥30 km 行程的距离)`），这样通勤线路也会生成模板。
2. 记录页顶部那张卡**改成按「你最近的线路」排序**（`RoutePlan.kt:603-607` 的默认值从「最近走过」改成
   「最近走过且距离最近的那条」），并在卡上标一行「上次开：2026-10-24 · 49.8 公里」。
3. `RoutePlan.kt:502-519` 的 `socAtNext` 改为**复用 `ConsumptionModel.trueRangeKm`**（同一套温度/爬升/余量修正），
   或至少：① 用 `consumption.whSample(实际均速)` 代替写死的 90 km/h；
   ② 乘上 `0.90` 的到站余量；③ 在站行下面注明「按 90 km/h · 未含低温修正」。
4. 给 `RouteTemplate` 加一个「日常线路」标记：`isCommute = distanceKm < 80`，
   通勤线路的余量表用**区间**（起点电量 → 终点电量）而不是「中途充电站」，标题写「到公司剩 X%」。

### P1-6 ｜ **体验改进** ｜ 告警没有统一入口、没有排序、没有历史，也没有「车被动了」

**证据**
- `api/alerts.go` 全文只有两种判定：**胎压**（越界 / 单胎离群）与**数据过期**。
  其余告警（保养超期、锁车未知、服务器连不上、电量 <20%）都是客户端各写各的横幅。
- `StatusScreen.kt:379-401` 保养横幅在最顶；`:432-449` 数据没上报横幅第二；

1. **新增「今日要注意」区**（`StatusScreen.kt`，放在保养横幅**之后**、主角数字**之前**，
   但只在有**近 7 天内发生变化**的条目时出现）：
   - 判定口径统一放在服务端（沿用 ADR #21/#22 的「唯一事实源」原则），新增
     `GET /api/v1/cars/{id}/alerts`，返回 `{code, severity, title, detail, since, is_new}` 数组。
   - 条目：`tpms_abnormal`、`vehicle_moved`（里程表比上次读取时涨了 > 1 km 且当前位置 ≠ 上次位置）、

   - `severity` 三档：`urgent`（红，置顶）/ `watch`（琥珀）/ `info`（灰，折叠）。
   - **「多久会变」决定排序**（沿用 v0.20.0 已经写下的那条原则）：
     `urgent` 按「今天就会变」排，`watch` 次之，`info` 全部沉到页面底部。
2. **`vehicle_moved` 判定需要客户端记住上次读数**：`StatusCache` 已在存上次状态，
   加一个 `lastOdometer` / `lastPosition` 字段（`StatusCache.kt`），App 每次成功读数后比对，
   「里程表比上次打开时多了 N 公里、位置变了」就生成一条 `urgent` 告警。**这是你每天真正会关心的一条**。
3. **胎压告警上提**：当 `tpms_alert == true` 或 `tpms_live_alert == true` 时，
   在车况页**主角数字上方**插一条红色横幅（`NoticeBanner` 的红色变体），
   而不是让胎压红轮子埋在页面底部。横幅文案直接用服务端给的 `tpms_alert_detail`。
4. **告警历史**：服务端 `alerts` 表（新建）记录每次告警的 `raised_at` / `cleared_at`，
   App 在「设置 → 告警历史」里能看到「3 天前左后胎压 2.61 bar，已恢复」。

## 3. 如果只能改三件事

**第一：P0-1 汇总卡两个「充电费用」行互相矛盾。**
理由：这是唯一一个**会让用户彻底不信任这个 App** 的问题。其他问题都是「少了点东西」，
只有这一个是「App 自己打自己的脸」。一个每天用、拿它当权威数据的人，
看到同一张卡上「未记录」和「≈ ¥1,837.31」并存，第一反应就是「这数不可信」——
而「每公里成本」恰好是 v0.25.0 花了整整一轮做出来的新功能，
它现在**被自己旁边那行「未记录」废掉了一半**。
改造成本极低（删一个 `else` 块 + 改三行文案），收益是让整个成本功能重新可信。

**第二：P0-2「现在能开」在停车态用高速档算，且低温不修正也不说。**
理由：这是你**每天真正会看的那一个数**，而且是唯一会在你通勤里**翻转决策**的数。
20% 电量时它说「58 公里，到不了公司」，而按你自己的通勤能耗（161.8 Wh/km）是 67 公里，到得了。
再叠加冬天**不修正、也不说**，等 12 月这个数就开始系统性骗人。
修它不需要新数据：市区档有 46 个样本，够用；低温样本不够就**明说「不修正」**，
这本来就是这个项目一贯的口径纪律（`data-dictionary.md` §3 整张表都在讲「不知道就写不知道」）。

**第三：P0-3「1 年」名不副实（23% 覆盖）+「这个月」根本没有。**
理由：这条直接命中「**这个月我花了多少钱**」这个你每天/每周都会问的问题，
而且是唯一一条「**在数据不足时仍然给出具体数字**」的顶层问题。
一个用 85 天冒充 365 天的「年度回顾」，配一个「每公里成本 ≈ ¥0.21」的结论，
拿去和自己的真实账单对不上，你会**回头去查是不是 App 算错了**。
修它的成本也不高：服务端加一个 `calendar_month` 窗口 + `coverage_days` 两个字段，
客户端加一段「本月」和一行覆盖率提示。

> 备选第四（如果前三件里有两件被排掉了，我会把它提上来）：**P1-4「家充/公共桩」按交直流猜且无法纠正**。
> 它是「每公里成本」的地基 —— 地基歪了，上面三个数字再准也没用。

## 4. 我明确不要的改动

1. **不要给「记录」页再加卡片。** 那一页现在首屏是「线路余量表」（长途）+ 时间轴，
   我每天要的是**昨天到今天的充电和行程**。如果再加一块「本月电费」「通勤摘要」，
   我会直接放弃这个 App。请**把长途余量表按「你最近的线路」排序**（P1-5），或者在通勤线路占多数时**自动折叠掉**。

2. **不要把「1 年」的图表做得更花哨。** 我不需要月度柱状图的动画。
   我需要的是**一行字告诉我「这只覆盖 85 天」**。信息没到位之前，视觉上的丰富只会让那个数更像真的。

3. **不要做「远程控车 / 启动空调 / 预约充电」。** ADR #2 已经定了只读，我同意。
   我要的是「App 把话说准」，不是「App 能替我做事」。

4. **不要把保养提醒彻底删掉，也不要把它改回红色。** v0.20.0 把它从红改成中性是对的方向，
   但**位置**改错了 —— 它该沉底，不该占第一屏。我要的是**位置**调整，不是颜色回滚，也不是删除。

5. **不要引入「账户 / 登录 / 多租户 / 分享」。** ADR #17/#23 说得很清楚：这是单人单车的自用工具。
   把复杂度花在多用户上，就是花在没人用的地方。

6. **不要把「真实可达续航」换回官方的「预估续航」。** 现在这个数虽然有上面 P0-2 说的毛病，
   但它的**方向**是对的（用车自己的实测 Wh/km，而不是 EPA 标称值）。
   我宁可要一个**诚实的、带置信度的**数，也不要一个看起来权威的 EPA 数。

7. **不要给告警加声音 / 震动 / 通知。** 告警该有的是**排序和「今天会不会变」**，
   不是更多打扰。ADR #20 已经定了提醒走 Hermes 推微信/飞书，我同意。

8. **不要在「记录」页把充电和行程再拆成两个 Tab。** v0.8.5 把它们合成一条交替时间轴是对的
   （充电永远发生在两次行程之间），别退回去。

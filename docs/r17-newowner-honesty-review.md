# r17 · 新手车主诚实性评审

> **评审人**：李女士（29 岁，购车 3 个月，家里刚装 7kW 国标家用充电桩，节假日跑 500 公里去外省）
> **唯一标尺**：诚实性 —— 数据不足的时候，App 承认「我不知道」，还是**编一个数字**？
> **评审对象**：TeslaMate 私有部署 Android 客户端（v0.25.0）+ 自建 Go API
> **评审日期**：2026-10-25
> **证据来源**：源码 `文件:行号` + 只读 SQL 复算 + 活接口取数 + 截图 `C:\tm-shots\r15\ r17\`
> **本次评审未改动任何代码、配置或数据**（只读评审；落地由主控统一执行）。

## 0. 一句话结论

这个 App 有一个很罕见的优点：**在「锁车状态」「数据新鲜度」「这条线没有你的充电记录」这类地方，它非常诚实**，甚至是刻意的（代码里写着「一个会撒谎的缓存比没有缓存更糟」）。

但它有一个**系统性的缺陷**：凡是「让数字看起来更完整」的地方，它倾向于**把推断当事实呈现**，而这些推断的前提（家充、冬季、电芯健康）在这台车上**根本不成立**。

最刺眼的一条，先放在这里：

> **App 的用量页会告诉我「家充电占 3%」—— 而这个数据库里一场家充都没有。**
> 那 58 度「家充」是**四川甘孜康定的酒店、四川阿坝的民宿、广西梧州的路边**；
> 而真正发生在**我家楼下 3 公里内**的 3 场充电（28.5 度），全被算成了「公共桩」。

这不是精度问题，是**归因反了**：App 嘴上说的「家充」和物理事实上的「家充」是两组完全不同的充电。

## 1. 场景逐个走查

### 1.1 家充：App 认得出吗？我能自己标吗？标了有用吗？

#### 我看到什么

把 App 装好、第一次去看「记录 → 充电记录」：

- 汇总卡（`ui/ChargeListPage.kt:86-143`，截图 `r17\02-charge-list.png`）：
  `1737 度 · 共 69 次充电` / `直流 1685 度 · 65 次` / `交流 52 度 · 4 次` / `2026年7月 至 2026年10月`
- 每一行的标签是三档：**特斯拉超充 / 国标直流 / 交流慢充**（`ui/ChargesScreen.kt:352-402`）
- 「用量」页底部有一块「充电费用」：
  `按你填的电价估算（家充 58 度 / 公共桩 1806 度）· 家充电占 3%。分母是行驶里程 8756 公里。`
  （`ui/StatsScreen.kt:391-421`）
- 「设置 → 电价」页有三个输入框：**家充电价（元/度）** / 公共桩电费 / 公共桩服务费
  （`ui/SettingsScreen.kt:1186 / 1198 / 1210`）

#### 我信不信

**列表页我信，用量页我不信。**

列表页写「交流慢充」，这**是事实** —— 桩的相数确实是 1 相、确实是交流。这个我认。

但用量页把它叫成「**家充**」，我就必须问一句：**凭什么？**

我去翻了库（只读 SELECT）：

```
geofences                    = 0 行
charging_processes            = 78 场
  其中 geofence_id NOT NULL   = 0 场      ← 没有任何一场充电知道自己在哪个桩/哪个围栏
  其中 cost NOT NULL          = 0 场
```

于是「家充」这个标签只可能来自一个判据：**是不是直流**。
`api/queries.go:150-163`（`cteChargeDC`）→ `api/queries.go:382` → 客户端 `ui/ChargeCost.kt:88-97`：

```kotlin
if (c.is_dc) { publicKwh += used; publicMinutes += ... } else { homeKwh += used }
```

**「非直流」= 「家充」。** 就这一条。

我按这条判据把库里 78 场复算了一遍，然后逐场去查它到底在哪儿：

| 场次 id | 时间 | 时长 | 充入 | 交流/直流 | **实际地点** | 距家 |
|---|---|---|---|---|---|---|
| 10 | 09-17 03:31 | 1 分 | 0.0 度 | 交流 | 上水径路（深圳） | — |
| 43 | 10-02 14:57 | 54 分 | 4.5 度 | 交流 | **四川 甘孜 康定 黄金坪** | 1500+ km |
| 44 | 10-02 16:53 | 617 分 | 17.0 度 | 交流 | **四川 甘孜 康定 黄金坪**（同一处） | 1500+ km |
| 45 | 10-03 14:37 | 636 分 | 29.7 度 | 交流 | **四川 阿坝 新桥乡** | 1500+ km |
| 61 | 10-06 18:52 | 33 分 | 0.7 度 | 交流 | **广西 梧州 龙腾路** | 900+ km |

**家里 3 公里内的充电会话：0 场。**（`charging_processes` JOIN `positions` + Haversine，家 = 新湖路 22.57548/113.8605）

家里 3 公里内实际发生的，是 **3 场直流**（id 66 / 13 / 3，共 28.5 度，最近一场 10-17）。

**结论：这台车在 App 的账本里，「家充 3%」是彻头彻尾的编造。**

更让我警觉的是，**项目自己的注释里已经把这个错误固化了**：

- `ui/ChargeCost.kt:48-50`：「实测 id=44 插枪 617 分钟只充入 17 度（有效功率仅 1.65 kW），家充绝不能按分钟算」
  —— id=44 是**康定黄金坪**的一处酒店，不是家。
- `ui/ChargeStats.kt:52-53`：「实测 id=44 插枪 617 分钟只充入 17 度」
- `ui/ChargeCost.kt:26-29`：「实测本车 97% 的电来自公共直流桩，家充（交流）只有 3.0%」

也就是说：**代码里那个「家充」的范例，是一次 1500 公里外的酒店充电。** 后面所有的费用拆分（「家充电占 3%」「公共桩边际成本」）都建立在这个错误前提上。

#### 我能不能自己标？

**不能。** 我在 App 里找不到任何地方能标「这场是家充」「这场是公共桩」「这个桩是 XX 服务区」。

- 充电详情页（`ui/ChargesScreen.kt`）全是只读展示；
- `geofence_id` 在服务端是 `charging_processes` 的列，但 App 侧**没有任何写入路径**（ADR #2「只读」）；
- 设置页只有一个**全局电价表**，不能按场次标注（`SettingsStore.kt:72-142`）。

所以你问的「标了之后 App 有没有用这个信息」——**它连标的地方都没有，自然也没地方用。**

#### 为什么

这个 App 的作者其实**知道**这个问题。`docs/CHANGELOG.md:114-120` 写着：

> **家充场次无法自动识别** —— 库里没有「家充」标记，当前靠「交流 + 低功率 + 跨夜」推断，主人应在设置页确认。

但**产品里没有落实这句话**：代码里的判据不是「交流 + 低功率 + 跨夜」，而是**只看「交流」**；而且「主人应在设置页确认」这一步**在设置页里根本不存在**。

ADR #12（`docs/adr.md`）其实早就用另一条路绕开了这个问题：

> **充电费用** | 界面移除 | 显示「未记录」| cost 全库 NULL，展示价值为零；配 tou_rates 后可恢复

**v0.25.0 把费用加回来了**（改用用户填的电价），但**把「家充 vs 公共桩」这个原本被删掉的问题又请回来了**，而且用了一个错误的判据。这是本轮最严重的问题。

#### 分类

| # | 问题 | 分类 | 严重度 |
|---|---|---|---|
| H-1 | 用量页「家充 / 公共桩」拆分用「直流/交流」冒充「家/公共」，本机 0 场家充 | **真 bug** | **P0** |
| H-2 | 费用模型里的「家充」范例（id=44）是 1500 km 外的酒店充电 | **误导性表述** | **P0** |

### 1.2 长途规划：我敢信吗？它用的是我的实测还是官方表？

#### 我看到什么

「记录」页顶部有一张「线路余量表」（`ui/RoutePlan.kt`），折叠时一行摘要，展开是完整的余量剖面 + 沿途充电站。

好的一面，**必须先说**：

- 结论句带来源限定：`按 2026-10-07 那趟实测：需充 2 次 · 第 252 公里低于 20% 保底`
  （`ui/RoutePlan.kt:232-248`）
- 卡片副标题：`按这条线路上真实发生过的充电推算（最近一次 2026-10-07）`（`ui/RoutePlan.kt:835`）
- 没有补电点时明说：`这条线路上没有你的充电记录 —— 没有可参考的补电点。`（`ui/RoutePlan.kt:885`）
- 站位详情区分「典型」与「仅 1 次实测」（`ui/RoutePlan.kt:935`）

**「按 X 月 X 日那趟实测」这种来源限定是有的，而且做得很克制。这是我信任它的起点。**

#### 但是，有三个地方我在出发前会误判

**(a) 它没有我「要跑 500 公里去外省」的那条线路。**

我查了库：

```
>=200km 的长途行程：11 趟，最长 344 km
100-200km：9 趟
其余 341 趟 <20km
```

**没有任何一趟 ≥350 km。** 而且这 11 趟其实是**同一次川藏大环线被充电切碎的片段**（深圳 → 贵州 → 四川康定 → 四川阿坝）：

```
09-22 南头立交→乐驿        259 km
09-23 港南大道→?           243 km
09-23 ?→蔚来换电站         236 km
09-23 蔚来换电站→汕昆高速   279 km
09-23 汕昆高速→母鸡山       229 km
09-24 苏南路→云南驿服务区    245 km
10-05 建设南路→合江荔乡服务区 315 km
10-06 金斛路→遵义绕城高速    217 km
10-06 贵阳农产品交易市场→G210 344 km
10-06 ?→金田服务区          257 km
10-07 广昆高速→城东路        252 km
```

`ui/RoutePlan.kt:388-437` 的「把 leg 串成 journey」逻辑，判据是「上一段终点 key == 下一段起点 key」（key = 围栏名或地址第一段）。**但 `geofences` 是 0 行**，key 只能落到反向地理编码的地址第一段（"南头立交"、"乐驿"、"G210"、"?"…），**串不上**。实测只有 `?→蔚来换电站 → 蔚来换电站→汕昆高速 → 汕昆高速→母鸡山` 这一条 3 段能接上。

**结果：App 会给我看 9~11 条「线路」，每条 217~344 km，每条都标「走过 1 次」。** 其中「广昆高速 → 城东路 252 公里」看起来最像一条完整路线，其实只是那次 1200 公里大环线的**最后一段**。

**而对我「国庆跑 500 公里去外省」这个真实需求，App 一句话都没有。** 它没有「输入目的地」的能力（`ui/RoutePlan.kt:64-68` 明说了不做路线规划 API），也没告诉你「你还没跑过这么远的线」。

更糟的是：`ui/RecordsScreen.kt:466` 是 `if (routePlan != null) { ... }`。
**如果我一条 ≥200 km 的线都没跑过，这张卡会**整个消失**，连「没有长途记录」都不会显示** —— 我会以为这个 App 根本没有长途功能。

**(b)「到下一站剩 X%」这个数，界面不说是怎么算的。**

展开后每个站会显示：`距下一站 128 公里 · 到下一站剩 45%`（`ui/RoutePlan.kt:949-967`）。

我追代码，这个数是这么来的（`ui/RoutePlan.kt:502-519` + `ui/RecordsScreen.kt:244-256`）：

```kotlin
val whPerKm = consumption?.let { m -> planSpeedKph?.let { m.whSample(it)?.bucket?.whPerKm } }
// planSpeedKph = 90.0   ← 硬编码
val needKwh = gapKm * whPerKm / 1000.0
val needPct = (needKwh / batteryCapacityKwh * 100).roundToInt()
```

我复算了这个模型（`api/queries.go:229-231` 的 `wh_per_km` 口径 + `ConsumptionModel.kt:171-196` 的分桶）：

| 车速档 | 样本数 | 中位 Wh/km | 样本温度范围 | 样本日期范围 |
|---|---|---|---|---|
| 0–60 | 46 | 168.6 | 10.4 ~ 36.8 °C | 07-31 ~ 10-24 |
| 60–90 | 26 | 174.3 | 8.3 ~ 32.5 °C | 08-22 ~ 10-24 |
| 90–110 | 11 | 183.0 | 16.6 ~ 28.0 °C | 09-22 ~ 10-06 |
| 110–130 | 5 | 197.4 | 19.0 ~ 33.3 °C | 09-22 ~ 10-06 |

`planSpeedKph = 90.0` → 命中 90–110 档 → **183.0 Wh/km，来自 11 条样本，全部集中在 9/22~10/6，温度 16.6~28.0 °C**。

三个问题：

1. **这 11 条样本是 9 月底到 10 月初的南方秋天数据。** 我要在 12 月跑同一条线，它会拿这 11 条秋天的值去算，**而且不做任何温度修正**。
2. **界面不显示这个数的来源**：不说是哪一档、几条样本、什么时候测的。用户只看到「到下一站剩 45%」这个精确到个位的数。
3. **「到下一站」的语义可能是错的**：充电必然打断行程（实测 78/78 场充电都落在某趟行程的起点或终点附近），所以「下一站」经常是**上一趟的收尾**或**这一趟的开头**，不是中途的一个服务区。`ui/RoutePlan.kt:215-231` 的注释自己也承认过这个问题（「那 2 次其实是上一趟的起点充电」）。

**(c)「20% 保底」是硬编码的，但界面像一个普适真理。**

`ui/RoutePlan.kt:180-181`：`belowFloorKm` = 第一个 `soc < 20` 的点；`ui/RoutePlan.kt:860-861` 图上画一条「20% 保底」线。
这个 20% 是个好经验值，但它是**这个 App 定的**，不是车厂建议、也不是我能改的。界面没有任何地方说「20% 是 App 选的阈值」。

#### 我信不信

- 「按 X 那趟实测：需充 N 次」→ **信**。它确实来自历史。
- 「按这条线路上真实发生过的充电推算」→ **信**。
- 「到下一站剩 45%」→ **半信**。它内部口径是对的（用的是我的实测 Wh/km，不是官方表），但**没有温度修正、没有样本量、没有日期**，而这是一张要在出发前 5 分钟看的表。
- 「这条线路是 252 公里、走过 1 次」→ **不信这是完整线路**。它是一条被充电切碎的片段，App 没告诉我。
- **「我 500 公里去外省」→ App 帮不了我，而且它连「帮不了」都没说。**

#### 分类

| # | 问题 | 分类 | 严重度 |
|---|---|---|---|
| R-1 | ≥200 km 的 11 趟被拆成 9~11 条「线路」，每条标「走过 1 次」，不说明它们其实是同一次旅程 | **误导性表述** | **P0** |
| R-2 | 没跑过长途时整张「线路余量表」消失，没有空状态 | **体验改进** | P1 |
| R-3 | 「到下一站剩 X%」不标 Wh/km 来源/样本量/日期，且**不做温度修正** | **误导性表述** | **P1** |
| R-4 | 「20% 保底」阈值来源不明 | **体验改进** | P2 |

### 1.3 电池健康：「占铭牌 84.9%」和「相对首测 98.4%」，哪个是我能看懂的？

#### 我看到什么

用量页「电池健康」卡片（截图 `r17\03-battery.png`，代码 `ui/StatsScreen.kt:584-657`）：

```
现在还能装        65.2 度
历史最好时        66.4 度
新电池标称        76.8 度
占铭牌            84.9%
相对首测          98.4%

「占铭牌」= 可用容量 ÷ 铭牌毛容量，两者不是同一口径，它不是「衰减了多少」。本车实测上限 86.4%。
「相对首测」= 当前容量 ÷ 首测容量（取前 3 次中位数），不受行驶能耗常数影响，是看衰减更准的那个数。
[曲线] 可用容量（度）· 纵轴已放大到数据范围 · 仅 83 天 / 9936 公里
```

我到库里复算了一遍服务端口径（`api/handlers.go:967-1091`、`api/queries.go:462-491`），活接口取到的值：

```
current_capacity_kwh      = 65.170      现在还能装
max_capacity_kwh_strict   = 66.370      历史最好时（严格档：只取充到 100% 的点）
nominal_capacity_kwh      = 76.800      新电池标称（NOMINAL_BATTERY_KWH，见 .env:24）
health_percent            = 84.857%     占铭牌
health_percent_of_baseline= 98.442%     相对首测
baseline_capacity_kwh     = 66.202      首测（= 前 3 次的中位数）
capacity_kwh_energy       = 65.796      能量反推口径（充入 kWh ÷ ΔSOC% × 100）
series_span_days          = 83
odometer_span_km          = 9935.6
series 点数               = 29（2026-08-02 → 2026-10-24）
```

#### 我信不信

**「占铭牌 84.9%」我信它是算对了，但我不知道它是什么意思。**

App 自己也说了（`ui/StatsScreen.kt:603-604`）：「两者不是同一口径，它不是『衰减了多少』」。
**那我作为新手车主拿它怎么办？** 一辆 3 个月的新车显示 84.9%，我第一反应是「电池已经掉 15% 了？！」—— 这正是「怕被数字骗」的人会被吓到的地方。解释在下面第三行小字里，字号比数字小得多。

**「相对首测 98.4%」我更信，但有一个致命的前提没告诉我。**

「首测」= **2026-08-02 附近的前 3 次测量**，也就是说：
- 分母不是新车的容量，是**一个已经衰减过的测量值**；
- 基准日是 **2.5 个月前**，不是提车那天。

所以「相对首测 98.4%」真实含义是：**「我的电池比 8 月 2 号那次测量低了 1.6%」**。
一个新手很容易把它读成「我的电池还有出厂水平的 98.4%，那三年后是不是还有 88%？」—— **这个外推是错的**，因为分母本身就不是出厂值。

App 说了「取前 3 次中位数」，但**没有说「首测是 2026-08-02」**，也没说「分母不是新车」。曲线 x 轴从 08-02 起，但我得自己看图猜。

**还有一件事，App 一点没说：这两个数都是「容量」，不是「续航」。**

我真正想知道的是：**「按你这台车现在的状态，冬天实际能跑多少公里？」**

这个数 App 有能力算（它已经有可用容量 65.2 度、已经有分档实测 Wh/km），但**它没有算，也没有任何地方接近这个数**。
App 给我的是「现在能开 189 公里」（车况页），那是**当前气温 27.5 °C** 的数；冬天同样的电、同样的车，续航会掉一大截，**而 App 永远只按当前气温显示，从不提示「这是夏天的数」**。

**它少给我的第三个数**（我自己加的）：
「按当前可用容量 65.2 度 + 你实测的分档能耗 + 冬季低温修正，冬天实际能跑 ~XXX 公里」。

#### 分类

| # | 问题 | 分类 | 严重度 |
|---|---|---|---|

| 「怎么算的」展开 | ❌ 只有 `按平时 130 km/h 估算 · 28°C · 参考 19.7 kWh/100km（借用 110–130 档）` | `ui/StatusScreen.kt:729-763` |

**最刺眼的：车况页那个「现在能开 189 公里」是全 App 最没有来源标注的数字。**

我把它的模型完整复算了一遍（`ConsumptionModel.kt:124-156` + `api/queries.go:229-231`）：

```
输入行程：car_id=1 全部 362 趟（api.drives(carId, 500)，上限 500）
可用样本：88 趟（distance≥20km、avg_speed>0、50≤wh_per_km≤400）
样本日期：2026-07-31 → 2026-10-24（85 天）
样本气温：8.3 °C ~ 36.8 °C
  其中 ≤10 °C 的样本：1 条
  其中 <15 °C 的样本：5 条
分桶：0-60=168.6(46) / 60-90=174.3(26) / 90-110=183.0(11) / 110-130=197.4(5)
巡航速度代理：130 km/h（speed_max≥100 的 80 条行程的峰值速度中位数）
```

所以「189 公里」这个数是：**85 天、88 条样本、气温 8~37 °C 的实测 Wh/km**，乘以一个**只对高温生效**的温度修正。

#### 关键问题：冬天怎么办？

`ConsumptionModel.kt:142-146` 自己写着：

```kotlin
// 温度修正：只做热的，不做冷的（库里 <10°C 样本不足，做了是编数据）。
val tempFactor = outsideTempC?.let { 1.0 + minOf(0.10, 0.006 * maxOf(0.0, it - 22.0)) } ?: 1.0
```

**在 6.5 °C 的冬天，tempFactor = 1.0 —— 等于完全不做低温修正。**
作者的选择本身是**诚实的**（「样本不足，做了是编数据」），但**界面没有把这件事说出来**：

「怎么算的」展开后写的是 `按平时 130 km/h 估算 · 28°C · 参考 19.7 kWh/100km（借用 110–130 档）`。
那个 **「28°C」紧挨着 Wh/km**，读起来就是「这个数已经考虑过温度了」。
实际上：**它只可能考虑过热。** 冬天 6 °C 时，这一行会变成 `· 6°C`，但数值一点不变 —— 而 6 °C 恰恰是最该修正的时候。

而且这行小字**默认是折叠的**（`ui/StatusScreen.kt:764-783`，`怎么算的 ▸`）。
**一个不想深究的用户永远看不到它。**

**再补一句：整站没有任何一个地方写着「我的数据只覆盖 2026 年 7 月到 10 月，没有冬季」。** 我翻了全部客户端代码，搜 `冬季` / `覆盖` —— 命中 0 次。

### 🟡 P2-11　三个容量口径并存，只给了两个

`续航×效率 65.17` / `严格档上限 66.37` / `能量反推 65.80`（活接口 `capacity_kwh_energy`）三个数，界面只显示前两个（`ui/StatsScreen.kt:585-609`），第三个在 API 里躺着。建议以「能量反推」为**主口径**（不依赖任何可调常数），另两个作为交叉校验，并说明差值来源。

### 🟡 P2-12　「该站历史」的分组键会因坐标抖动拆站

`ui/ChargeStats.kt:152-161`：`围栏名 → 坐标聚类（2 位小数 ≈ 1.1 km）→ 地址第一段`。`geofences` 为空时**永远走坐标聚类**，1.1 km 外挪一点车就变成「另一个站」，历史功率/耗时被拆成两份。建议：坐标聚类放宽到 3 位小数（≈110 m）并做半径合并。

## 4. 作为新手车主，我最想要 App 诚实告诉我的三个数

> 「别人说三年会掉续航，我很怕被数字骗。」—— 我不需要更多数字，我需要**能追溯、能问「这个数从哪来」的数字**。

### ① 「这辆车现在实际能跑多少公里？」

- **现在给我的**：`189`（副行「留 20% 保底还能开 168 公里」），来源说明折叠在「怎么算的 ▸」里。
- **我想要的**：`现在能开 189 公里` + **常驻**的 `按 2026-07-31~2026-10-24 的 88 条实测（8~37°C，无冬季样本；低温不修正）`。
- **为什么这个数对我重要**：这是我出发前唯一要拿来和「下一个服务区还有多远」比对的数。它必须能被追问。

### ② 「我充的电里，多少是在家充的，多少是在外面充的？」

- **现在给我的**：`家充 58 度 / 公共桩 1806 度 · 家充电占 3%`。
- **真相**：一场家充都没有。那 58 度是四川甘孜的酒店、四川阿坝的民宿、广西梧州的路边；真正在家附近充的电（3 场直流）被算进了「公共桩」。
- **我想要的**：`直流 1806 度 · 交流 58 度（App 无法判断哪场是家充：库里没有围栏数据）` + 一个能让我自己标「这场是家充」的开关。
- **为什么这个数对我重要**：它直接决定「家充桩装得值不值」「我每公里到底花多少钱」。给我一个反的数，比不给这个数更糟。

### ③ 「按我现在的电池状态，冬天实际能跑多少公里？」

- **现在给我的**：**没有**。App 给我「占铭牌 84.9%」「相对首测 98.4%」两个我读不懂的百分比，和一个「用 85 天夏秋数据算的 189 公里」。
- **我想要的**：`冬季实际续航：暂无数据 —— 本车 10 °C 以下的实测行程只有 1 条，不足以给出冬季续航。`（等样本够了再给真数）
- **为什么这个数对我重要**：我三个月前装桩、节假日要跑 500 公里去外省（深圳冬天也要 5~10 °C）。**「冬天能跑多少」是我买这车之后最常问、但 App 从没回答过的一个数。** 我宁愿看到「我不知道」，也不想看到一个 27.5 °C 的数。

> **这三个数的共同点**：它们都不是「更多数据」，而是**给现有数字补上来源与边界**。
> 这个 App 已经做到了一半（长途规划有「按 X 那趟实测」、电池有「仅 83 天 / 9936 公里」、离线有「上次读到 · X 前」）。
> 缺的那一半，正好落在**我真正会做决策的三个地方**：续航、费用、冬天。

## 5. 最后一句

这个 App 的作者是我见过的**最会自我怀疑的开发者**：代码里到处是「⚠️ 别把『没取到』伪装成『没这功能』」「一个会撒谎的缓存比没有缓存更糟」「样本不足，做了是编数据」。

**问题在于 —— 这些自我怀疑都写在代码注释里，没有一条变成界面上对用户的承诺。**

我在车况页看到的仍然是一个没有出处的 `189`；
我在用量页看到的仍然是 `家充电占 3%`；
我翻遍全 App，仍然找不到一句「我的数据只覆盖 7 月到 10 月，没有冬季」。

**把注释里的诚实，搬到界面上，就是这个 App 从「好用」变成「可信」的最后一步。**

| 版本 | 我引入的 bug |

## 一、仍未落地（按「会不会让用户做错决定」排序）

### P0-1 · 地点归一不是**聚类**，而且 `place_key` **会漂**

**出处**：第 21 轮数据口径审计 P1-2 / P1-3

- `cteAddrNorm` 的实现是「每个地址各自认 500 m 内**被引用最多**的那个邻居」——
  **不传递、不对称**，所以不是聚类。
- 实测：267 个地址 → 214 个 canonical；500 m 内共 **137 对**，
  其中 **124 对合并、13 对拿到不同 key**。
- 非传递性的实证链：地址 11—14 相距 **284.3 m**、14—16 相距 **370.2 m**，
  而 11—16 相距 **654.4 m**；
  结果 `canonical(11)=11`、`canonical(14)=11`、`canonical(16)=14`、
  `canonical(15)=15` ⇒ **15 与 16 相距 450.3 m 却拿到两个不同的 place_key**。
- `canonical` 依赖**实时**的 `uses` 计数 ⇒ **新增记录可能翻转** canonical，
  同一地址的 `place_key` 随之改变 ⇒ 客户端「首尾 key 相等 ⇒ 回到同一地」
  的判断**无声失效**。
- 围栏命中还会把 key 从 `a<id>` 变成 `g<id>`（本机 `geofences` 现有 1 行「家」，
  而 78/78 场充电的 `geofence_id` 仍为 NULL）。

**影响**：实测只命中 **1 趟**真实行程（id=295，2026-10-01，1.8 km），
所以现在是 **P1 而不是 P0**。

**建议规格**：
- 改成**传递闭包**聚类（递归 CTE），或至少把链上的地址统一；
- `place_key` 用**分量内最小 id**（永远稳定，不随 `uses` 变），
  而**显示名**仍取分量内被引用最多的那个（名字更好看）；
- 代价：会改变一部分 `place_key` 的取值 ⇒ 必须重跑冒烟 + 逐站对账。

### P0-2 · 没有「我从第 N 站出发」的入口

**出处**：第 23 轮车主复审 P2-3

复审的批评：
> 「我出发前真正要问的是「**我这次从第 N 站开始，下一站是哪、要充到多少**」，
> App 没有任何入口让我选起点（chips 只选**线路**，不选**站**）。」

v0.39.0 已经在站列表顶部加了「**需要注意的 N 跳**」摘要（实测那条线 36 跳里 4 跳），
这解决了「**哪几跳要动手**」，但仍没解决「**我现在在哪一跳**」。

**建议规格**：折叠态 chips 下面加一排「从第 N 站出发」的横向 chip
（数据全在 `JourneyStop` 里，**零新依赖**），
选中后折叠态主角改成「**下一站：汕昆高速 · 280 公里 · 要充到 100%**」。

**难点**：App 其实**知道车现在在哪**（`/status` 的 `odometer`），
但那条线路是**过去**跑的（车现在在家 = 那趟的终点），
所以「按当前位置」与「按这次重跑」是两个不同的问题，**别混**。

### P1-1 · 「估 ≥ 保底 但真 < 保底」只覆盖了**到站**一种情形

**出处**：第 23 轮车主复审 P1-1（已在 v0.38 落地）

已落地的判据：`estSoc >= RESERVE_SOC && realSoc < RESERVE_SOC` → 告警。
本机验证：11 个「低于 20% 保底」告警 **11/11 成立**、误报 **0**。

**仍缺**：**中途**跌破保底（不是到站时跌破）——
`/route_profile` 的真实剖面里有 **104 个**跌破 20% 的采样点（区间 227~6066 公里），
而现在的告警只看**站到站**的落点。
**建议规格**：用真实剖面找「这一跳中途最低多少」，
低于保底就在这一跳上标 ⚠（剖面数据服务端已有，客户端已拉）。

### P1-2 · 误差带是**模型残差**，不是**端到端到站误差**

**出处**：第 23 轮数据自洽性审计 P2-5

实测那条线 35 跳的「估算 − 真值」：中位 **+4.5 点**、最大 **+26 点**、方向**偏乐观**；

   > ⚠️ **v0.43.0（第 26 轮口径审计）补注：这个数字在当前代码 + 当前数据上**复现不出来**。**
   > 独立复刻得到的是：**中位 +2、乐观侧最大 +11、保守侧最小 −12**，
   > 而且方向分布是 **22 正 / 12 负 / 1 零** —— 是**双侧**的，不是单向乐观。
   > 原始的「+4.5 / +26」出自第 23 轮审计，当时没有写清口径
   > （是否含第一跳、是否含爬升修正、哪一版模型），**已不可复现**。
   > ⇒ App 现在**不再引用这两个数**，改成从**这条线自己的每一跳**现算、给**区间**。
   > 本条留在这里是为了说明它已被作废，**不要当成事实引用**。
而界面上的 ±N 是**模型自身残差**的 90 分位（±12 点）——
**低估了最坏情况**。

v0.39.0 已把措辞改成「模型残差约 ±N 个点」（不夸大），
但**数字本身**仍偏乐观。

**建议规格**：
- 要么把误差带按**端到端实测**校准（需要保存每跳的实测残差）；
- 要么在无解跳的「要 N 个点」上给**区间**（复审实测：建设南路 103、真实需 92~112）。

### P1-3 · 车轮功率口径的爬升模型漏了**下降坡度项**

**出处**：第 21 轮口径审计 P1-5

毛耗电回归（`api/climb.go`）**不含 `g_down`** ⇒ `c_up` 偏高 **7.8%**
（6.4295 → 5.9260），补上后 R² 0.6685 → **0.7323**。

⚠️ **v0.34.0 起这套系数已降级为「物理交叉核对」**，客户端**不再**用它的值
（客户端用标定法口径 + delta-grade）。
所以现在是 **P2 而不是 P1**。

### P1-4 · `avg_speed_kph` 用取整后的 `duration_min`

**出处**：第 23 轮数据自洽性审计 P2-6

`api/queries.go`：`round(distance / duration_min * 60)::int`
—— `duration_min` 是整数分钟 ⇒ 速度最大偏 **2.0 km/h**。
`ConsumptionModel` 按 `avg_speed_kph` 选 Wh/km 档，
99 条可用样本里 **2 条**靠近分档边界。

**建议规格**：用 `end_date − start_date`（秒级）算均速，
`end_date` 为 NULL 时回落到 `duration_min`。

### P2-1 · 归一后**地址的 POI 名**取自 canonical

**出处**：第 21 轮口径审计 P1-1（**已在 v0.34 落地**）

`poi_name` / `poi_type` 改取**原地址**（canonical 只作兜底）。
实测：充电 session 62（2026-10-07，61.28 kWh）原来显示「梧州市第五中学」，
现在显示「**中石化富民加油站**」。

### P2-2 · `avg_power_kw`（采样均值）与 `avg_power_kw_true`（时间加权）

**出处**：第 23 轮数据自洽性审计 P1-1（**已在 v0.38 落地**）

同一场充电在两个页面给两个数，最大差 **45.9%**（id=25：54 kW vs 37 kW）。
行程页已改用 `effectiveAvgPowerKw()`（时间加权）。

### P2-3 · 充电实测样本混进**交流**场次

**出处**：第 21 轮口径审计 P1-4（**已在 v0.36 落地**）

30 场有效实测里有 **3 场不是快充**（最慢一场 **576 分钟**）。
`measuredSamples` 现在只收 `is_dc` 的场次。

### P2-4 · 电池衰减的「台阶」是**老化**还是**重新校准**，数据分不出来

**出处**：第 22 轮车主复审（定性意见）

复审原话：
> 「"9/28 掉 0.56 度"和"BMS 重新校准了一次"**在数据上长得一模一样**，App 说不清是哪个。」

实测：9/28 前后 66.11 → 65.79/65.83 → 65.67 → 65.27，
之后 3560 公里一直在 64.99~65.41 之间横着走。

**建议规格**：在电池卡上**明说**这两者无法区分，
并说明「容量口径 = 续航估值 × 效率常数，续航估值本身是 BMS 的估算」。

## 二、明确**不做**的事（避免下轮重提）

| 事项 | 理由 |
|---|---|
| **TOU 分时电价接线** | 库里 `tou_rates` **0 行**、`charging_processes_tou_cost` **0 行**、引擎函数齐全但**未配置**；而这台车**78 场充电 0 场在家**，分时电价对它**零价值**。做一个永远返回「未配置」的端点是**假功能** |
| **阶梯电价（居民阶梯）** | 同上 —— 阶梯只作用于家充，而这台车没有家充。且阶梯按**结算月累计电量**分档，窗口聚合**算不出来**，必须先有结算月口径 |
| **自动识别通勤 / 推断家与公司** | 87 天里 62 个工作日中只有 29 天有行驶记录；工作日 17~21 点回到「家」300 m 内 **0 次** |
| **按目的地 → 规划余量** | 需要高德路径规划 API；且通勤只有 33 公里、家里有桩 |
| **每周通勤柱状图 / 日历热力图** | 62 个工作日里只有 29 天有行驶记录，图表会把「没开车」渲染成「App 漏数据」 |
| **在 App 里画/写充电围栏** | `geofences` 是 TeslaMate 的事实源 |
| **能耗曲线加爬升第三维** | 第 19 轮爬升评审明确不建议：一屏一个主角会破、每根柱的样本口径无法解释 |
| **把 `socRingDiameterDp` 系数改成 4.255** | fs=2.0 的环会变成 238 dp，在 360 dp 屏上占 73% 宽度，视觉比重**压过主角** |

## 三、已被复审**否定**的判断（记录下来，别再提）

| 判断 | 复审结论 |
|---|---|
| 「分时电价与阶梯电价是费用链路的最后一环，应该这轮就做」 | 第 23 轮车主复核与对抗性审计都确认：对这台车**零价值**（0 场家充），且引擎未配置 |
| 「爬升修正的高估来自系数口径不同源」 | 成立，但**主导因素是「分子取上一段」**（错段）—— 独立复算实测：错段单项造成 4 次判定翻转、累计 +16.6 kWh；口径混用造成 +12% 偏差。**两者都要修** |
| 「`effects/noise` 是个可用的显著性判据」 | 不是。它是「端到端变化 ÷ 单点残差 σ」，而斜率的显著性取决于 `SE(斜ope) = σ/√Sxx` |
| 「电池衰减是线性的，回归斜率就是衰减速率」 | 序列**不是直线**：含一次 −0.5624 度的阶跃（R² 0.641 → 0.829，F=15.41 显著），朴素斜率高估 **2.31 倍** |
| 「`drives.ascent` 是物理高差，所以 c_up÷(m·g) 就是传动效率」 | 能量自洽性算出 **142% > 100%**（物理不可能）⇒ `drives.ascent` **不是**物理高差，「隐含效率 78%」不成立 |
| 「短途的能耗残差和长途一样大」 | 不一样：全样本 P90 = 97.4 Wh/km（351 km 上 ±52 点，毫无意义），km≥100 的 P90 = 23.2（±12.4 点） |

## 一、爬升能耗模型（**最高价值，尚未落地**）

评审已把系数**算出来并交叉验证**，缺的是「把它接进模型」。

### 已确认的事实

| 量 | 值 | 来源 |
|---|---|---|
| 上坡系数 `c_up` | **6.29 Wh/m**（n=99 趟，R²=0.62） | 整趟功率积分，毛耗电 `max(P,0)` 与回充 `max(−P,0)` 分开拟合 |
| 隐含传动效率 | 5.042 / 6.29 = **80.2%** | 物理区间 75~90% ✓ |
| 下坡回充系数 `c_regen` | 3.40 Wh/m（n=3 纯下坡）→ **不可宣称实测**，取保守值 **3.0** | 分裂半 2.68~3.56（±15%） |
| 必须是**加性** | 交互项 −0.007，R² 只 +0.0002；分速带斜率 20~80 km/h 恒为 5.6~6.9 | 多项回归 |
| **不能用净爬升** | J1 净爬升只有 +3278 米（毛爬升 51,791） | 往返线路终点比起点低 |
| 「爬升显著」判据 | 用**坡度 ≥ 1.0 m/km**，不用总米数 | 400 km 爬 200 m 只值 1.4 Wh/km，100 km 爬 200 m 值 5.8 Wh/km |
| 噪声 | `drives.ascent` 与相邻点正高差**逐条精确相等**（439/439）；但含 GPS 量化噪声（长途 0.8%~2.3%、短途 17.1%） | 去噪要用「同里程锚点取高程中位数」 |

### 待办

1. **服务端** `GET /cars/{id}/climb_model`：逐趟算毛耗电与回充 → 多元 OLS 拟合 → 下发
   `c_up` / `c_regen` / 样本量 / **每个系数各自的置信标记** / 分裂半结果。
   （客户端**只消费不算** —— 两套算法必然漂移，这是第 20 轮充电评审 P0-5 的教训。）
2. **客户端** `ConsumptionModel`：删掉 `if (ascentM >= 200) 1.05 else 1.0`（二值饱和且是乘性），
   改成 `whEff = bucket.whPerKm × tempFactor + climbWhPerKm`（加性）。
   入参从 `ascentM: Int?` 改成 `(ascentM, descentM, distanceKm)` 三元组。
3. **客户端** `StatusStore`：`recentAscentM = list.firstOrNull()?.ascent_m` 是**最近一趟**的爬升
   （常常是 2 km 挪车 = 0~4 m）→ 修正**几乎永不生效**。车况页应改为「当前行程实时爬升」或**不给数并说明**。
4. **客户端** `RoutePlan`：「到下一站剩 X%」加上爬升修正 + **20% 保底**，
   并**同时**显示「爬升多耗 X 度（−Y 个百分点）」——
   只改数字不解释，用户会以为 App 坏了；只解释不改数字，用户不知道该不该提前充。
5. **文案**：「51,791 米 ≈ **5.9 座**珠峰」（不是 1.4 座 —— 51,791 ÷ 8,849 = 5.85）。

## 二、服务端 TOU 引擎接线（**引擎齐全，入口为零**）

库里已有 `compute_tou_cost` / `lookup_tou_rate` / `trigger_compute_tou` /
`tou_rates` 表 / `charging_processes_tou_cost` 旁路表，`api/` 里 **0 处引用**。

⚠️ **三处文档说「配了 `tou_rates` 就能恢复显示」是错的** —— 已于 v0.32.0 订正
（`docs/adr.md` ADR#12、`docs/api-spec.md`、`docs/data-dictionary.md`）：
TOU 引擎把结果写进**旁路表** `charging_processes_tou_cost.cost_tou`，
**从不写** `charging_processes.cost`。

**待办**：
- `GET /cars/{id}/cost_summary?mode=tou` → 读旁路表。
- 响应里的 `tou` 块必须能区分三种状态：
  `not_configured` / `partial` / `complete`，且 **`cost_yuan` 在非 complete 时必须是 `null`**，
  **绝不能返回 0**（0 会被读成「免费充电」，比不给数更糟）。
- 配套只读 `GET /api/v1/tou/status`：`tou_rates` 条数 / 覆盖的围栏 / `backfill_all_tou` 最后执行时间。
- 写入端点另开一版（写库 + `audit_tou_config` 兜底 + 变更审计），不要和读端点混在一起。

## 三、阶梯电价（居民阶梯）

`ChargeRates` 现在只有单一单价，表达不了阶梯（按**结算月累计电量**分档，
不是「每度一个价」）→ **无法用窗口聚合计算**，必须知道结算月内的累计电量。

**待办**：
- `ChargeRates` 加 `homeTiers: List<HomeTier>`（`upToKwh` + `yuanPerKwh`）+ `billingMonthStartDay`。
- 服务端 `CostSummary` 增加**结算月内家充网侧度数的逐日序列**（`home_kwh_by_day`），
  客户端按累计量切档。
- 口径纪律：阶梯**只作用于家充**；夜间单一谷价不需要档。

## 六、已明确**不做**的事（避免下轮重提）

| 事项 | 理由 |
|---|---|
| **自动识别通勤 / 自动推断家与公司** | 实测：87 天里 62 个工作日中只有 29 天有行驶记录；工作日 17~21 点回到「家」围栏 300 m 内 **0 次**；严格定义下（工作日 + 家出发 + 20~60 km + 05~10 点）**只有 1 趟**。自动识别必然把长途当通勤 |
| 「按目的地 → 规划余量」 | 需要高德路径规划 API；且通勤只有 33 公里、家里有桩，通勤根本不需要规划充电 |
| 「通勤费用 / 每公里成本」卡 | 33 km × 0.2295 kWh/km ≈ 7.6 kWh ≈ 4.4 元，不值得一张卡，反而引入「钱算错了」的信任成本 |
| 每周通勤柱状图 / 通勤日历热力图 | 62 个工作日里只有 29 天有行驶记录，任何周图表都是残缺的，会把「没开车」渲染成「App 漏数据」 |
| 在 App 里画/写充电围栏 | `geofences` 是 TeslaMate 的事实源，App 去写会与 TeslaMate 抢 |
| 能耗曲线加爬升第三维 | 见上文第 3 条 |
| 把 `socRingDiameterDp` 系数改成 4.255 去追 0.235 的不变量 | fs=2.0 的环会变成 238 dp，在 360 dp 屏上占 73% 宽度，视觉比重**压过主角** |
